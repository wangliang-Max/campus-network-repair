# 答辩提纲

## 一、项目介绍（1 分钟）

- 选题：T05 校园网络与机房故障报修平台
- 角色：报障人、网络技术员、管理员
- 主线：报修单从提交到关闭的全流程状态追踪

## 二、技术方案（3 分钟）

1. **分层结构**：Controller → Service → Mapper，Entity / DTO / VO 分离
2. **认证**：BCrypt 存密码，JWT 无状态认证，拦截器统一校验，白名单放行登录与文档
3. **权限**：`@RequireRole` 注解 + 角色拦截器；数据层再做本人校验，防水平越权
4. **状态机**：状态与合法流转集中在 `OrderStatus` 枚举，非法流转直接拒绝
5. **数据一致性**：状态流转、状态日志、处理记录在同一事务；`@Version` 乐观锁防并发
6. **查询**：MyBatis-Plus 分页 + XML 多表 JOIN，一次查出报障人/设备/机房，避免 N+1
7. **统计**：平均修复时长、未关闭数、按机房与状态分组

## 三、演示顺序（2 分钟）

1. `GET /api/health` 证明服务正常
2. `admin` 登录 → 设备分页查询
3. `stu07` 新建报修单 → `tech01` 受理 → 开始维修 → 修复完成
4. `stu07` 验收通过 → 查看详情中的状态轨迹
5. 重复受理，展示 400 非法流转
6. `stu01` 查看他人单据，展示 403
7. `tech01` 查看统计概览

## 四、常见问题

**Q1：为什么用状态机，不在 Service 里写 if？**
状态和合法流转集中在一个枚举里，新增状态只改一处；非法流转有统一校验，不会因为漏写 if 而放过。

**Q2：乐观锁怎么实现的？**
`repair_order.version` 加 `@Version`，MyBatis-Plus 更新时自动带 `WHERE version = ?` 并自增；更新行数为 0 说明被别人抢先处理，抛业务异常让用户刷新。

**Q3：为什么不用悲观锁？**
报修单冲突概率低，悲观锁会长时间占连接；乐观锁只在更新瞬间判断，适合这种场景。

**Q4：防重复提交怎么做的？**
同一报障人 + 同一设备 + 存在未关闭单据时拒绝；另外单号唯一索引兜底。

**Q5：怎么防越权？**
两层：接口层 `@RequireRole` 控制角色；数据层校验 `reporterId` 是否等于当前用户，技术员/管理员才可跨人查看。

**Q6：JWT 怎么退出登录？**
当前为无状态 Token，退出由前端删除；如果要服务端强制失效，可加 Redis 黑名单或短 Token + 刷新 Token。

**Q7：事务边界在哪？**
每次状态流转方法加 `@Transactional`，状态更新、日志、处理记录、设备状态联动要么全成功要么全回滚。

**Q8：为什么平均修复时长从 status_log 算？**
`repair_order` 没有关闭时间字段，`status_log` 里 `to_status='CLOSED'` 的时间就是关闭时刻，避免冗余字段不一致。

**Q9：项目还有什么不足？**
没有前端；没有接入 Redis 缓存与消息通知；统计只做了概览，未做时间趋势；这些是后续可扩展方向。
